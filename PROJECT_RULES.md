## Build and Tooling

### Prerequisites

Use a Node.js version permitted by the root manifest, npm, Docker with Compose support,
and SSH access to a disposable or explicitly approved pfSense target.

### Commands

Use the root `dev`, `prod`, `check`, `build`, `deploy`, `clean`, `changelog`, and
`recipes` commands for repository-wide work. Nova orchestrates the root, API,
documentation, and private Docker assembly workspaces from the configuration in
`nova.config.json`.

| Command                                             | Purpose                                                           |
|-----------------------------------------------------|-------------------------------------------------------------------|
| `npm run dev --workspace pfsense-actions-app-api`   | Run the Express service with `apps/api/.env` and the Vite console |
| `npm run check --workspace pfsense-actions-app-api` | Run the generated lint, type, and test checks                     |
| `npm run build --workspace pfsense-actions-app-api` | Transpile the service and build the console into `build/admin`    |
| `npm run deploy:container`                          | Build and start the repository-wide Docker Compose service        |

### Environment Variables

Every environment variable is optional. The administrator account is created only on
the console's first-run setup screen, never from environment values or files. The
database encryption key is generated into the data volume, and no setting supplies
one. The pfSense SSH variables are deprecated: they only seed a new database and log a
warning at every start. Never commit or bake credentials into the image.

## Workspace Rules

### Workspace Inventory

#### Nova Workspace Boundary

- The service lives in `apps/api` on Nova's Express.js scaffold and contributes its compiled output to the repository-wide container appliance.
- Treat the migrated routes, schemas, README, and SSH methods as a behavioral contract
  to review, not as a reason to weaken Nova's generated standards.
- Keep the service narrow; the migration is not permission to add pfSense management
  features.
- Keep the operations console limited to controller state: tokens, redacted activity,
  the tested SSH connection, and the administrator's own sign-in security. It must not
  become a firewall configuration surface.
- Generated Nova rules apply without migration-specific rule exceptions. The React
  console in `src/web/`, its types in `src/types/web/`, and `mock-api.mts` share one
  documented exception block (`console-interface` in `apps/api/eslint.config.mts`) for
  rules that don't fit JSX, browser APIs, and React hooks; keep it limited to those files.
- Retain `assets/legacy/` configuration and packaging files until the replacement deployment
  path has been reviewed.

## Architecture and Data

### Architecture

#### API Contract Rules

- One route maps to one allowlisted operation; never accept a command string from a
  request.
- Authenticate and rate-limit requests before opening an SSH connection.
- Validate every parameter against a closed schema with realistic size and range bounds.
- Prefer POST for operations that cause side effects. Any compatibility route using GET
  must be documented, tested, and scheduled for removal.
- Serve the API under `/api/v1`. The original root paths `/`, `/system`, `/ping`, and
  `/wol` are documented, tested compatibility aliases until a deliberate major release
  removes them.
- Return every error as `{ error: { code, message, issues? } }` with a stable code.
- Give each action a bounded execution time and a stable mapping from internal failures
  to HTTP status codes.
- Preserve data-minimizing responses unless a specific response field is reviewed for
  sensitivity and added to the contract.
- Keep health and readiness routes free of privileged firewall data.
- Version breaking route or schema changes deliberately; do not silently reinterpret
  existing input.

#### pfSense Adapter Rules

- Keep SSH connection management and pfSense command definitions behind one narrow
  adapter.
- Commands must be constants or assembled from validated typed values with safe
  argument handling.
- Never interpolate an untrusted address, MAC, interface, path, or option directly into
  a shell command.
- Always disconnect in a `finally` path after a successful connection attempt.
- Distinguish authentication, connection, timeout, command, and validation failures in
  internal errors while keeping public responses minimal.
- Make retry behavior explicit. Do not automatically repeat an operation that may have
  succeeded unless it is proven idempotent.
- Configure SSH host-key trust deliberately; do not silently accept a changed host key.

### Error Strategy

| Layer            | Strategy                                                                             |
|------------------|--------------------------------------------------------------------------------------|
| Environment      | Fail startup with path-specific validation errors before listening                   |
| Authentication   | Return an authentication failure without revealing which credential check failed     |
| Request schema   | Reject invalid input before SSH work with a stable client-error response             |
| pfSense adapter  | Wrap failures into typed internal categories and always clean up sessions            |
| Route handler    | Map typed failures to the public status contract and log a redacted cause            |
| Unexpected error | Return a generic server failure and retain diagnostic context only in protected logs |

## Project Guardrails

### Security, Privacy, and Secrets

#### Authentication and Secret Rules

- Client personal access tokens, SSH passwords, private keys, and host trust material
  are secrets.
- Authenticate clients with scoped personal access tokens. Store live controller state
  in embedded SQLite without requiring an external database service.
- Store only SHA-256 token hashes on the server. Raw tokens belong exclusively to their
  clients and must have at least 256 bits of random entropy.
- Keep scopes closed and route-specific: `pfsense:read`, `reachability:read`, and
  `wol:execute`. Client tokens never grant browser administration.
- Return `401` for missing, malformed, unknown, or expired tokens and `403` when a valid
  token lacks the required scope.
- Never print a supplied or generated personal access token to application logs. The
  explicit token-generation command and authenticated console may each show a new raw
  value once as provisioning output.
- Do not place secrets in command-line arguments, image layers, committed files, error
  responses, snapshots, or test fixtures.
- Compare credentials with a timing-safe mechanism appropriate to their representation.
- Apply console token changes immediately through the shared state boundary. Revoking a
  record must invalidate public requests without a restart.
- Require HTTPS for every request that crosses a trusted host boundary because Bearer
  credentials are reusable until expiry or revocation.
- Prefer SSH key authentication. Password and private-key updates from the console must
  pass a live SSH test before replacing working settings, remain write-only over HTTP,
  and persist only as authenticated ciphertext in the protected controller data volume.
- Notification destination secrets, such as tokens, passwords, and webhook URLs, are
  encrypted with the database encryption key, like the SSH credentials, and never
  returned after saving. If the key is lost, they are removed and the affected
  destinations stay paused until the secrets are entered again.
- Redact authorization headers, credentials, private keys, commands containing sensitive
  values, and raw SSH errors from logs.

#### Operations Console Rules

- Authenticate the console with a local username and Argon2id password hash; never
  accept a client token or pfSense username and password as the console login.
- Create the administrator account only through the first-run setup screen, using the
  one-time code printed in the container log while no account exists.
- Exchange local credentials for an HttpOnly, SameSite-strict browser session that lasts
  24 hours. Store only a hash of each session in SQLite so restarts don't sign the
  administrator out, and resolve the account from the database on every request.
- Ask for an authenticator or recovery code only after the password passes, as a
  separate step.
- Require CSRF protection, sent in the `X-CSRF-Token` header, and separate login
  throttling of 10 failed attempts per client address every 15 minutes for every
  state-changing browser request.
- Trust `X-Forwarded-*` headers only from private and loopback addresses, derive the
  public origin from each request, and bind each passkey to the hostname it was added
  on. There is no public URL or trusted-proxy setting.
- Never return token hashes, stored SSH passwords, or private-key contents through the
  administrative API. New raw personal tokens may be returned once at creation.
- Require the current administrator password for username or password changes,
  authenticator setup and removal, new recovery codes, and adding or removing passkeys.
  A password change invalidates every other browser session.
- Manage notification destinations only from a signed-in console session. Requests that
  carry a client token get `403` and can never read or change them.
- Treat activity as a curated audit surface, not unrestricted container-log access. Store
  bounded action names, outcomes, actor identifiers, timestamps, and summaries only.
- Keep `/admin` behind HTTPS and preferably add reverse-proxy network or identity controls
  for internet-accessible deployments.

### Platform and Domain Rules

#### Current Action Boundaries

- **Connectivity:** establish an authenticated session and report only controller-level
  success or failure.
- **System information:** run `uname -mrs` and return only the validated operating system,
  release, and architecture fields.
- **Ping:** accept a validated IP address and bounded count; reject options or hostnames
  that could alter command parsing unless deliberately supported.
- **Wake-on-LAN:** validate canonical MAC and broadcast-address input before execution.

Adding another action requires its user problem, pfSense command, privilege level,
inputs, idempotency, timeout, response semantics, and tests to be documented first.

#### Docker and Operations

- Build a reproducible image through Nova's Docker integration.
- Keep the public `Dockerfile`, `compose.yml`, and `.dockerignore` at the repository root and private s6 assembly under `packages/docker`.
- Compile the API and its required dependency closure inside the root-context multi-stage Docker build; never consume a host build directory.
- Run the HTTP process as a non-root user with a read-only root filesystem where
  practical.
- Start s6 initialization as root, validate `PUID`, `PGID`, and `TZ`, and drop the API longrun directly to the configured numeric identity.
- Change ownership only for declared writable mount roots. Never recursively rewrite ownership across existing volume contents during startup.
- Mount or inject credentials at runtime; never copy them into the image.
- Store mutable controller state in a dedicated non-root `/data` volume with restrictive
  permissions, including the SQLite database and the generated `keys/installation.key`.
- Provide liveness for the Express process and readiness that reflects completed startup
  validation without repeatedly connecting to pfSense.
- Handle SIGTERM and SIGINT by stopping new requests, allowing bounded active work to
  finish, closing SSH sessions, and exiting within the grace period.
- Set explicit HTTP, SSH connection, and command timeouts.
- Send alerts in the background with a 10-second limit per send and no retries. Run the
  5-minute scheduled SSH check only while a destination that isn't paused wants the
  pfSense alerts and the pfSense password or key is saved.
- Emit structured, redacted logs with request correlation and action names.
- Put internet-accessible deployments behind an HTTPS reverse proxy or private overlay,
  and never publish the service's plain-HTTP listener directly.
- Never require secrets to start the container. The administrator account comes from the
  setup code, and the database encryption key is generated into the data volume, where it
  always lives; never bake either into an image. Create
  client tokens through the console and persist later console changes only in the protected
  data volume.

## Testing and Verification

### Test Strategy

- Unit-test request schemas, authentication, failure mapping, and command construction.
- Use an SSH adapter fake for ordinary route tests; automated tests must not require a
  live production firewall.
- Add integration coverage for middleware order, rate limits, timeouts, connection
  cleanup, and graceful shutdown.
- Test command-injection payloads and malformed address or MAC inputs explicitly.
- Verify every container build starts with documented configuration, reports health, and
  terminates cleanly.
- Use a disposable lab firewall only for opt-in end-to-end verification.

### Required Verification

Run the root and affected workspace checks, build the production service and appliance,
and use only an approved disposable lab for opt-in pfSense end-to-end verification.
