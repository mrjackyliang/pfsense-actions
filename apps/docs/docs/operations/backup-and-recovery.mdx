Back up the <Terminology title="The one SQLite file that holds everything" to="/docs/reference/terminology#storage-and-backups">controller database</Terminology> and its <Terminology title="Locks saved secrets; lose it and they're wiped" to="/docs/reference/terminology#storage-and-backups">encryption key</Terminology> so you can restore pfSense Actions without recreating tokens or settings.

## Choose an Export or Data Volume Backup

Use a portable <Terminology title="A JSON backup that can hold secrets in plain text" to="/docs/reference/terminology#storage-and-backups">export file</Terminology> to move the pfSense connection, notifications, or stored token hashes into another installation. It does not need the source <Terminology title="Locks saved secrets; lose it and they're wiped" to="/docs/reference/terminology#storage-and-backups">encryption key</Terminology>, and the import leaves the destination account, sign-in security, sessions, and activity history in place, adding one `backup-imported` event to that history.

Use a complete <Terminology title="The Docker volume that keeps your data across updates" to="/docs/reference/terminology#storage-and-backups">data volume</Terminology> backup to restore the installation as a whole. It keeps the administrator account, sign-in security, sessions, activity history, database, and encryption key together, as well as the connection, notifications, and token hashes.

[Export and Import](/docs/console/pfsense-connection/#export-and-import) covers the portable flow. The sections below cover the complete volume copy.

## What to Back Up

| Item                                                                                                                                                          | Why it matters                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
|---------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| The <Terminology title="The Docker volume that keeps your data across updates" to="/docs/reference/terminology#storage-and-backups">data volume</Terminology> | It holds `database/pfsense-actions.sqlite3` with every token, setting, <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destination</Terminology>, and activity record, and the generated key in `keys/installation.key` that opens the saved pfSense credential, the authenticator app, and each <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">destination</Terminology>'s <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology>. |

The backup holds the password hash, each <Terminology title="All that's stored of a token; lose it and you replace it" to="/docs/reference/terminology#access-tokens">token hash</Terminology>, and the encrypted credentials and notification secrets, and with the generated key it can decrypt them. Raw tokens and raw <Terminology title="A one-use backup code for when your phone is gone" to="/docs/reference/terminology#console-sign-in">recovery codes</Terminology> aren't in it.

It's recommended to store the backup encrypted.

## Back Up the Data Volume

1. Stop the service so the database files are consistent.

   ```bash
   docker compose stop app
   ```

2. Copy the volume's contents into an archive, using any image that has `tar`.

   ```bash
   docker run --rm \
     -v pfsense-actions_pfsense_actions_data:/config:ro \
     -v "$PWD":/backup \
     debian:trixie-slim \
     tar -czf /backup/pfsense-actions-data.tgz -C /config .
   ```

3. Start the service again.

   ```bash
   docker compose start app
   ```

- Compose names the volume `pfsense-actions_pfsense_actions_data` after the project name in `compose.yml`, and `docker volume ls` lists it.
- The archive includes the `database/` folder with the `-wal` and `-shm` files next to `pfsense-actions.sqlite3`, and the `keys/` folder.

## Restore

Replace the volume's contents with the archive, so the database and `keys/installation.key` come back from the same backup.

:::danger
The first command below deletes the current <Terminology title="The Docker volume that keeps your data across updates" to="/docs/reference/terminology#storage-and-backups">data volume</Terminology> before the backup replaces it.
:::

```bash
docker compose down --volumes
docker compose up --no-start
docker run --rm \
  -v pfsense-actions_pfsense_actions_data:/config \
  -v "$PWD":/backup:ro \
  debian:trixie-slim \
  tar -xzpf /backup/pfsense-actions-data.tgz -C /config
docker compose start app
```

On the next start, initialization assigns the restored tree to `PUID:PGID` and restores the contract modes on `keys/` and `keys/installation.key`.

## Lost Administrator Password

There's no password reset. To get back in, restore a backup from a time you knew the password, or reinitialize as described below.

A <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkey</Terminology> still signs you in, but changing the password asks for the current one.

## Lost Authenticator

- With a <Terminology title="A one-use backup code for when your phone is gone" to="/docs/reference/terminology#console-sign-in">recovery code</Terminology>, sign in with it in place of the authenticator code. Then open **Sign-in and security**, turn off the authenticator app, and set it up again on your new device.
- With a <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkey</Terminology>, sign in with it and do the same.
- Without either, delete `keys/installation.key` with the command in [Encryption Key Doesn't Match](#encryption-key-doesnt-match) and restart pfSense Actions. The authenticator app is then turned off so the password signs you in, but the saved pfSense credential and the notification secrets are removed too, as described in [Lost Encryption Key](#lost-encryption-key).
- Restoring a backup made before the authenticator app was turned on also works.

## Lost Encryption Key

When `keys/installation.key` is missing, pfSense Actions makes a new <Terminology title="Locks saved secrets; lose it and they're wiped" to="/docs/reference/terminology#storage-and-backups">encryption key</Terminology> and starts. Secrets locked with the old key can't be opened anymore, so it removes them and keeps everything else.

- **Removed** — The saved pfSense password or private key, the authenticator app, which is turned off with its <Terminology title="A one-use backup code for when your phone is gone" to="/docs/reference/terminology#console-sign-in">recovery codes</Terminology>, and every <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destination</Terminology>'s <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology>.
- **Kept** — The administrator account and password, <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkeys</Terminology>, <Terminology title="Keeps you signed in to the console for 24 hours" to="/docs/reference/terminology#console-sign-in">browser sessions</Terminology>, tokens, settings, the <Terminology title="Who did what and when, for the newest 250 events" to="/docs/reference/terminology#console-activity-and-secrets">activity log</Terminology>, the connection's address, port, username, and sign-in method, and each <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">destination</Terminology>'s name, <Terminology title="What happened that's worth an alert" to="/docs/reference/terminology#notifications">events</Terminology>, and plain fields.

### Log and Notice

On that start, the log names what was removed.

```text
2026-01-01T12:00:00.000Z WARN pfsense-actions: No encryption key was found at /config/keys/installation.key, so pfSense Actions made a new one. These saved secrets were locked with the old key and were removed: the pfSense password, the authenticator app for <username>. Enter them again in the console.
```

- The list says `the pfSense private key` instead when the connection signs in with a key, and it ends with `the <name> notification` for each <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destination</Terminology> that had <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology>.
- The <Terminology title="Who did what and when, for the newest 250 events" to="/docs/reference/terminology#console-activity-and-secrets">activity log</Terminology> records `encryption-key-replaced`.
- The console shows **Saved secrets were removed** at the top of every page, with a link for each item to enter again.
- <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">Destinations</Terminology> without <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology> that chose the **Saved secrets were removed** <Terminology title="What happened that's worth an alert" to="/docs/reference/terminology#notifications">event</Terminology> get it as an alert, as described in [Notifications](/docs/console/notifications/#after-a-lost-encryption-key).
- When nothing depended on the old key, as on a new installation, there's no warning and no notice.

### Enter the Secrets Again

1. Select **Enter the pfSense password** or **Enter the pfSense private key**, enter it on the **Connection** page, and select **Test and save**.
2. Select **Set up the authenticator app**, and turn it on again as described in [Account Security](/docs/console/account-security/#turn-on-an-authenticator-app).
3. Select the item for each <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">destination</Terminology>, such as **Set up the Ops chat notification again**. Then select **Edit** on it, enter its <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology>, and select **Save**, as described in [Notifications](/docs/console/notifications/#after-a-lost-encryption-key).

- Each item leaves the notice once it's entered again. **Dismiss** hides the notice, and anything not entered again stays removed.
- Until the credential is back, every <Terminology title="One fixed pfSense task you can call, like ping or wake" to="/docs/reference/terminology#core-concepts">action</Terminology> answers `503` with `connection_not_configured`, and a <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">destination</Terminology> gets no alerts until its <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology> are back.
- If the deprecated `PFSENSE_*` variables are still set, they fill the credential back in on the same start.

## Encryption Key Doesn't Match

When `keys/installation.key` belongs to another database, for example after a restore that mixed files, startup stops with this message until it's fixed.

```text
The encryption key at /config/keys/installation.key doesn't belong to this database. Put back the key file this database was created with, or delete /config/keys/installation.key and restart to make a new key, then enter the saved secrets again.
```

- If a backup has the key file this database was created with, put it back as `keys/installation.key` in the volume.
- Without that file, delete the key file and start again, which makes a new key as described in [Lost Encryption Key](#lost-encryption-key).

These commands delete the key file from the volume.

```bash
docker compose stop app
docker run --rm \
  -v pfsense-actions_pfsense_actions_data:/config \
  debian:trixie-slim \
  rm /config/keys/installation.key
docker compose start app
```

- An old key file put back after pfSense Actions made a new one stops startup the same way, because the database now belongs to the new key.
- A damaged key file stops startup with `The encryption key file at /config/keys/installation.key is not 64 hexadecimal characters.`, and the same two fixes apply.

## Change PUID or PGID with Existing Data

Set the new `PUID` and `PGID`, each from 1 through 60000, and recreate or restart the container. Initialization changes the owner of `/config` and everything under it on every start before the controller runs, so no separate `chown` container is needed.

## Reinitialize Deliberately

:::danger
Reinitializing deletes the administrator account, every token, the pfSense connection, the authenticator app and <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkeys</Terminology>, every <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destination</Terminology>, and the <Terminology title="Who did what and when, for the newest 250 events" to="/docs/reference/terminology#console-activity-and-secrets">activity log</Terminology>.
:::

1. Back up the current volume as described above.
2. Remove the <Terminology title="The Docker volume that keeps your data across updates" to="/docs/reference/terminology#storage-and-backups">data volume</Terminology> with `docker compose down --volumes`.
3. Start the service with `docker compose up --detach`, which creates a new database and key.
4. Create the administrator account with the new <Terminology title="The one-time code from the log that creates your login" to="/docs/reference/terminology#console-sign-in">setup code</Terminology> from the log.
5. Set up the pfSense connection, create new tokens, update every client, and add your <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destinations</Terminology> again.
