See what each part of a pfSense Actions deployment holds, how the <Terminology title="pfSense Actions itself, the go-between for your clients" to="/docs/reference/terminology#core-concepts">controller</Terminology> protects it, and which gaps to cover with your network setup.

## Why Use This Model?

1. Keeps the firewall credential in one place, so each client holds only its own token.
2. Checks every token and <Terminology title="What a token may do; each action needs exactly one" to="/docs/reference/terminology#access-tokens">scope</Terminology> before any SSH work starts.
3. Returns small JSON results, so firewall output doesn't leave through the API.
4. Lists the current limitations, so you can plan network controls around them.

## Tokens and Scopes

- Each token carries 256 bits of random data, and only its SHA-256 <Terminology title="All that's stored of a token; lose it and you replace it" to="/docs/reference/terminology#access-tokens">token hash</Terminology> is stored.
- Hashes are compared in constant time, and tokens are read from the database on every request, so a revocation applies at once.
- <Terminology title="What a token may do; each action needs exactly one" to="/docs/reference/terminology#access-tokens">Scopes</Terminology> are exact, and a request that fails the token or <Terminology title="What a token may do; each action needs exactly one" to="/docs/reference/terminology#access-tokens">scope</Terminology> check never reaches SSH.
- A token can't sign in to the console or change tokens, notifications, the connection, or sign-in settings, because those routes need a <Terminology title="Keeps you signed in to the console for 24 hours" to="/docs/reference/terminology#console-sign-in">browser session</Terminology> and answer a token with `403`.

## Console Protections

- **Separate account** — The <Terminology title="The one login for the console; tokens can't sign in" to="/docs/reference/terminology#console-sign-in">administrator account</Terminology> has its own Argon2id-hashed password, and tokens or pfSense credentials can't sign in. Unknown usernames take as long to reject as wrong passwords.
- **First-run setup** — Creating the account needs the <Terminology title="The one-time code from the log that creates your login" to="/docs/reference/terminology#console-sign-in">setup code</Terminology> from the container log. Each code lasts 30 minutes and works once, and the setup screen allows 10 wrong codes per address in 15 minutes.
- **Session cookie** — The session cookie is `HttpOnly`, `SameSite=Strict`, and `Secure` over HTTPS. A <Terminology title="Keeps you signed in to the console for 24 hours" to="/docs/reference/terminology#console-sign-in">browser session</Terminology> lasts 24 hours from sign-in, and the database stores only a hash of its value.
- **Change protection** — Every change needs the session's <Terminology title="A hidden per-session value that blocks forged changes" to="/docs/reference/terminology#console-sign-in">CSRF token</Terminology> in the `X-CSRF-Token` header. Changing the password ends every other session.
- **Password checks** — Setting up or turning off the authenticator app, making new recovery codes, adding or removing a <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkey</Terminology>, and changing the username or password all ask for the password again.
- **Backup confirmation** — Export and import require <Terminology title="A fresh sign-in check before export or import" to="/docs/reference/terminology#console-activity-and-secrets">Confirm it’s you</Terminology> with the password and current authenticator code, or with a <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkey</Terminology>. The in-memory grant lasts five minutes, works once, and is bound to that browser session and to either export or import.
- **Backup route boundary** — Only a signed-in browser session can confirm, export, preview, or import a backup. A personal access token cannot use those routes.
- **Sign-in limits** — Wrong passwords, wrong codes, rejected <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkeys</Terminology>, and wrong password confirmations share a limit of 10 failures per address in 15 minutes. Every route under `/api/v1` also allows 120 requests per minute per address. An IPv6 client counts by its `/56` network for both limits.
- **Second factors** — <Terminology title="The six-digit code from your authenticator app" to="/docs/reference/terminology#console-sign-in">TOTP</Terminology> codes can't be reused, and each <Terminology title="A one-use backup code for when your phone is gone" to="/docs/reference/terminology#console-sign-in">recovery code</Terminology> works once and is stored as a hash. <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">Passkey</Terminology> sign-in requires user verification and checks the origin, the hostname the passkey belongs to, and the signature counter.
- **Challenges** — A <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkey</Terminology> challenge works once, whether or not it succeeds. A sign-in challenge waiting for a code lasts 5 minutes and ends after 5 wrong codes.
- **Page headers** — Every response sends `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`, except the console's versioned files, which browsers may cache. Console pages add a strict Content Security Policy and `X-Frame-Options: DENY`.

## Data at Rest

- The <Terminology title="The one SQLite file that holds everything" to="/docs/reference/terminology#storage-and-backups">controller database</Terminology> is created readable only by the service's user, inside a folder only that user can open.
- The pfSense credential, the <Terminology title="The six-digit code from your authenticator app" to="/docs/reference/terminology#console-sign-in">TOTP</Terminology> secret, and each <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destination</Terminology>'s <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology> are encrypted with the <Terminology title="Locks saved secrets; lose it and they're wiped" to="/docs/reference/terminology#storage-and-backups">encryption key</Terminology>, which is never written to the database. The generated key is always kept in `keys/installation.key` in the data directory, readable only by the service's user.
- A portable <Terminology title="A JSON backup that can hold secrets in plain text" to="/docs/reference/terminology#storage-and-backups">export file</Terminology> decrypts a selected pfSense credential and notification secrets into plain text so another installation can import them without the source encryption key. Access tokens remain stored hashes, and the import encrypts plain-text secrets with the destination key in one database transaction.
- When the key file is missing, pfSense Actions makes a new key, removes the pfSense credential and the <Terminology title="A destination's token or password, saved but never shown" to="/docs/reference/terminology#notifications">secret fields</Terminology> the old key sealed, and turns off the authenticator app, as described in [Backup and Recovery](/docs/operations/backup-and-recovery/#lost-encryption-key). A key file from another database stops startup instead.
- The administrator password is stored as an Argon2id hash, each token, session, and <Terminology title="A one-use backup code for when your phone is gone" to="/docs/reference/terminology#console-sign-in">recovery code</Terminology> as a SHA-256 hash, and each <Terminology title="Sign in with your device, no password or code needed" to="/docs/reference/terminology#console-sign-in">passkey</Terminology> as its public key only.

:::info
Encryption uses AES-256-GCM with a random 12-byte IV for each value. Password hashing uses Argon2id with 64 MiB of memory, 3 passes, and 2 lanes, a 16-byte salt, and a 32-byte hash.
:::

## SSH Credential and Host Keys

- A key is recommended over a password, and a key with a passphrase isn't supported.
- Each request opens its own SSH session and closes it when the request ends, and so does each <Terminology title="A sign-in every 5 minutes to notice pfSense going down" to="/docs/reference/terminology#notifications">scheduled check</Terminology>.
- The commands come from the <Terminology title="The only commands it will ever run on pfSense" to="/docs/reference/terminology#core-concepts">allowlist</Terminology> and take only validated values, and no route accepts a command string.
- pfSense Actions doesn't perform <Terminology title="Not done yet, so any server key is accepted" to="/docs/reference/terminology#pfsense-ssh-access">host key verification</Terminology>, so it's recommended to keep the network path to the firewall on a segment you trust.

## Current Limitations

- **HTTPS is external** — The listener serves plain HTTP, so HTTPS has to come from a <Terminology title="The HTTPS front door, like Caddy, ahead of the controller" to="/docs/reference/terminology#deployment-and-container">reverse proxy</Terminology> or another encrypted path.
- **No <Terminology title="Not done yet, so any server key is accepted" to="/docs/reference/terminology#pfsense-ssh-access">host key verification</Terminology>** — pfSense Actions accepts whichever host key the SSH server presents.
- **No command time limit** — A command that hangs keeps its request open, and only the SSH connection attempt times out, after 20 seconds.
- **No graceful shutdown** — Stopping the service ends requests and SSH sessions that are still running.
- **Forwarded headers from private addresses** — pfSense Actions trusts `X-Forwarded-*` from any private or loopback address, so a device on your network that can reach the listener directly can choose the address its <Terminology title="How many requests one IP gets before it's turned away" to="/docs/reference/terminology#access-tokens">rate limits</Terminology> apply to.
- **One firewall and one administrator** — Each deployment stores a single connection and a single account.
- **IP address only** — The firewall is configured by IP address, not hostname.
- **Minimal logs** — Logs are plain text without request IDs, and they explain a `502` only while **Debug logging** is on.
- **Local <Terminology title="Who did what and when, for the newest 250 events" to="/docs/reference/terminology#console-activity-and-secrets">activity log</Terminology>** — It keeps 250 events in the database and isn't tamper-resistant.
- **Alerts aren't retried** — A notification that can't reach its service in 10 seconds, or that the service refuses, isn't sent again, as described in [Notifications](/docs/console/notifications/#delivery).
- **Listens on every interface** — The Compose file publishes the port on every IPv4 and IPv6 address, and `npm run dev` and `npm run prod` listen on every interface, so devices on your network can reach the plain-HTTP listener unless you switch to a <Terminology title="Listen on 127.0.0.1 only, so just the host can reach it" to="/docs/reference/terminology#deployment-and-container">loopback binding</Terminology>.
