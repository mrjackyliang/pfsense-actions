See what each part of a pfSense Actions deployment holds, how the <Terminology title="the pfSense Actions service between clients and pfSense" to="/docs/reference/terminology#controller">controller</Terminology> protects it, and which gaps to cover with your network setup.

## Why Use This Model?

1. Keeps the firewall credential in one place, so each client holds only its own token.
2. Checks every token and <Terminology title="a named capability granted to a token" to="/docs/reference/terminology#scope">scope</Terminology> before any SSH work starts.
3. Returns small JSON results, so firewall output doesn't leave through the API.
4. Lists the current limitations, so you can plan network controls around them.

The <Terminology title="the pfSense Actions service between clients and pfSense" to="/docs/reference/terminology#controller">controller</Terminology> is one security boundary, and it doesn't replace network segmentation or pfSense's own access controls.

## Tokens and Scopes

- Each token carries 256 bits of random data, and only its SHA-256 <Terminology title="the SHA-256 digest stored instead of the token" to="/docs/reference/terminology#token-hash">token hash</Terminology> is stored.
- Hashes are compared in constant time, and tokens are read from the database on every request, so a revocation applies at once.
- <Terminology title="a named capability granted to a token" to="/docs/reference/terminology#scope">Scopes</Terminology> are exact, and a request that fails the token or <Terminology title="a named capability granted to a token" to="/docs/reference/terminology#scope">scope</Terminology> check never reaches SSH.
- A token can't sign in to the console or change tokens, notifications, the connection, or sign-in settings, because those routes need a <Terminology title="a 24-hour console sign-in stored in the database" to="/docs/reference/terminology#browser-session">browser session</Terminology> and answer a token with `403`.

## Console Protections

- **Separate account** — The <Terminology title="the single local console login, separate from tokens" to="/docs/reference/terminology#administrator-account">administrator account</Terminology> has its own Argon2id-hashed password, and tokens or pfSense credentials can't sign in. Unknown usernames take as long to reject as wrong passwords.
- **First-run setup** — Creating the account needs the <Terminology title="the one-time code printed in the log for first-run setup" to="/docs/reference/terminology#setup-code">setup code</Terminology> from the container log. Each code lasts 30 minutes and works once, and the setup screen allows 10 wrong codes per address in 15 minutes.
- **Session cookie** — The session cookie is `HttpOnly`, `SameSite=Strict`, and `Secure` over HTTPS. A <Terminology title="a 24-hour console sign-in stored in the database" to="/docs/reference/terminology#browser-session">browser session</Terminology> lasts 24 hours from sign-in, and the database stores only a hash of its value.
- **Change protection** — Every change needs the session's <Terminology title="a per-session value required on console changes" to="/docs/reference/terminology#csrf-token">CSRF token</Terminology> in the `X-CSRF-Token` header. Changing the password ends every other session.
- **Password checks** — Setting up or turning off the authenticator app, making new recovery codes, adding or removing a <Terminology title="a device-held credential for passwordless console sign-in" to="/docs/reference/terminology#passkey">passkey</Terminology>, and changing the username or password all ask for the password again.
- **Sign-in limits** — Wrong passwords, wrong codes, rejected <Terminology title="a device-held credential for passwordless console sign-in" to="/docs/reference/terminology#passkey">passkeys</Terminology>, and wrong password confirmations share a limit of 10 failures per address in 15 minutes. Every route under `/api/v1` also allows 120 requests per minute per address.
- **Second factors** — <Terminology title="a six-digit authenticator app code for sign-in" to="/docs/reference/terminology#totp">TOTP</Terminology> codes can't be reused, and each <Terminology title="a single-use code that stands in for an authenticator code" to="/docs/reference/terminology#recovery-code">recovery code</Terminology> works once and is stored as a hash. <Terminology title="a device-held credential for passwordless console sign-in" to="/docs/reference/terminology#passkey">Passkey</Terminology> sign-in requires user verification and checks the origin, the hostname the passkey belongs to, and the signature counter.
- **Challenges** — A <Terminology title="a device-held credential for passwordless console sign-in" to="/docs/reference/terminology#passkey">passkey</Terminology> challenge works once, whether or not it succeeds. A sign-in challenge waiting for a code lasts 5 minutes and ends after 5 wrong codes.
- **Page headers** — Every response sends `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`, except the console's versioned files, which browsers may cache. Console pages add a strict Content Security Policy and `X-Frame-Options: DENY`.

## Data at Rest

- The <Terminology title="the SQLite file that holds the controller's state" to="/docs/reference/terminology#controller-database">controller database</Terminology> is created readable only by the service's user, inside a folder only that user can open.
- The pfSense credential, the <Terminology title="a six-digit authenticator app code for sign-in" to="/docs/reference/terminology#totp">TOTP</Terminology> secret, and each <Terminology title="a place pfSense Actions sends alerts to" to="/docs/reference/terminology#notification-destination">notification destination</Terminology>'s <Terminology title="a destination setting sealed with the encryption key" to="/docs/reference/terminology#secret-field">secret fields</Terminology> are encrypted with the <Terminology title="the 64-character key that seals stored secrets" to="/docs/reference/terminology#encryption-key">encryption key</Terminology>, which is never written to the database. The generated key is always kept in `keys/installation.key` in the data directory, readable only by the service's user.
- When the key file is missing, pfSense Actions makes a new key, removes the pfSense credential and the <Terminology title="a destination setting sealed with the encryption key" to="/docs/reference/terminology#secret-field">secret fields</Terminology> the old key sealed, and turns off the authenticator app, as described in [Backup and Recovery](/docs/operations/backup-and-recovery/#lost-encryption-key). A key file from another database stops startup instead.
- The administrator password is stored as an Argon2id hash, each token, session, and <Terminology title="a single-use code that stands in for an authenticator code" to="/docs/reference/terminology#recovery-code">recovery code</Terminology> as a SHA-256 hash, and each <Terminology title="a device-held credential for passwordless console sign-in" to="/docs/reference/terminology#passkey">passkey</Terminology> as its public key only.

:::info
Encryption uses AES-256-GCM with a random 12-byte IV for each value. Password hashing uses Argon2id with 64 MiB of memory, 3 passes, and 2 lanes, a 16-byte salt, and a 32-byte hash.
:::

## SSH Credential and Host Keys

- A key is recommended over a password, and a key with a passphrase isn't supported.
- Each request opens its own SSH session and closes it when the request ends, and so does each <Terminology title="the 5-minute SSH check behind the pfSense alerts" to="/docs/reference/terminology#scheduled-check">scheduled check</Terminology>.
- The commands come from the <Terminology title="the closed set of commands the controller runs" to="/docs/reference/terminology#allowlist">allowlist</Terminology> and take only validated values, and no route accepts a command string.
- pfSense Actions doesn't perform <Terminology title="confirming the firewall's SSH identity before trusting it" to="/docs/reference/terminology#host-key-verification">host key verification</Terminology>, so it's recommended to keep the network path to the firewall on a segment you trust.

## Current Limitations

- **HTTPS is external** — The listener serves plain HTTP, so HTTPS has to come from a <Terminology title="the HTTPS front end that forwards to the controller" to="/docs/reference/terminology#reverse-proxy">reverse proxy</Terminology> or another encrypted path.
- **No <Terminology title="confirming the firewall's SSH identity before trusting it" to="/docs/reference/terminology#host-key-verification">host key verification</Terminology>** — pfSense Actions accepts whichever host key the SSH server presents.
- **No command time limit** — A command that hangs keeps its request open, and only the SSH connection attempt times out, after 20 seconds.
- **No graceful shutdown** — Stopping the service ends requests and SSH sessions that are still running.
- **Forwarded headers from private addresses** — pfSense Actions trusts `X-Forwarded-*` from any private or loopback address, so a device on your network that can reach the listener directly can choose the address its <Terminology title="a cap on requests per client address" to="/docs/reference/terminology#rate-limit">rate limits</Terminology> apply to.
- **One firewall and one administrator** — Each deployment stores a single connection and a single account.
- **IP address only** — The firewall is configured by IP address, not hostname.
- **Minimal logs** — Logs are plain text without request IDs, and they don't explain a `502`.
- **Local <Terminology title="a bounded, redacted history of actions and changes" to="/docs/reference/terminology#activity-log">activity log</Terminology>** — It keeps 250 events in the database and isn't tamper-resistant.
- **Alerts aren't retried** — A notification that can't reach its service in 10 seconds, or that the service refuses, isn't sent again, as described in [Notifications](/docs/console/notifications/#delivery).
- **Listens on every interface** — The Compose file publishes the port on every IPv4 and IPv6 address, and `npm run dev` and `npm run prod` listen on every interface, so devices on your network can reach the plain-HTTP listener unless you switch to a <Terminology title="publishing the port only on 127.0.0.1" to="/docs/reference/terminology#loopback-binding">loopback binding</Terminology>.
