Use the two `pfsense:read` routes to confirm that the <Terminology title="pfSense Actions itself, the go-between for your clients" to="/docs/reference/terminology#core-concepts">controller</Terminology> can reach the firewall and to read its basic system details.

## Why Use These Routes?

1. Tests the whole path, from the token to the firewall, in one request, so monitoring can tell a firewall problem from a client problem.
2. Returns three validated fields instead of raw `uname` output, so clients get a stable shape.
3. Needs only the read-only `pfsense:read` <Terminology title="What a token may do; each action needs exactly one" to="/docs/reference/terminology#access-tokens">scope</Terminology>.

## Check Connectivity

`GET /api/v1/connectivity`, also at `GET /`, runs the <Terminology title="Can pfSense Actions sign in to pfSense? Yes or no" to="/docs/reference/terminology#api-actions">connectivity check</Terminology>. It signs in to the <Terminology title="The one pfSense box this install controls" to="/docs/reference/terminology#core-concepts">target firewall</Terminology> over SSH, runs `uname -mrs`, and signs out.

```bash
printf 'header = "Authorization: Bearer %s"\n' "$PFSENSE_ACTIONS_TOKEN" \
  | curl --config - --silent --show-error --fail-with-body \
      https://actions.example.net/api/v1/connectivity
```

```json
{
  "connected": true
}
```

- `200` means the sign-in and the command both succeeded, and `502` means either one failed.
- Each call opens an SSH session, so the Docker <Terminology title="Docker's 30-second check that the service is listening" to="/docs/reference/terminology#deployment-and-container">health check</Terminology> is the better fit for frequent liveness probes.
- To get an alert when the firewall stops answering, a <Terminology title="A sign-in every 5 minutes to notice pfSense going down" to="/docs/reference/terminology#notifications">scheduled check</Terminology> can do the polling for you, as described in [Notifications](/docs/console/notifications/#the-scheduled-check).

## Read System Information

`GET /api/v1/system`, also at `GET /system`, returns the firewall's <Terminology title="pfSense's OS, release, and CPU type, nothing more" to="/docs/reference/terminology#api-actions">system information</Terminology> as JSON.

```bash
printf 'header = "Authorization: Bearer %s"\n' "$PFSENSE_ACTIONS_TOKEN" \
  | curl --config - --silent --show-error --fail-with-body \
      https://actions.example.net/api/v1/system
```

```json
{
  "architecture": "amd64",
  "operatingSystem": "FreeBSD",
  "release": "14.0-CURRENT"
}
```

- The values come from `uname -mrs`, split on whitespace into the operating system, release, and architecture.
- Output that doesn't split into exactly three fields returns `502` instead of a partial body.
- The response leaves out the hostname, interfaces, configuration, and the raw command output.

## Responses

| Status | Error code                  | Meaning                                                                                                                                                                           |
|--------|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `200`  | —                           | The SSH sign-in and `uname -mrs` succeeded.                                                                                                                                       |
| `401`  | `authentication_required`   | The token is missing, malformed, unknown, or expired.                                                                                                                             |
| `403`  | `scope_required`            | The token doesn't have `pfsense:read`.                                                                                                                                            |
| `429`  | `rate_limited`              | The client reached a <Terminology title="How many requests one IP gets before it's turned away" to="/docs/reference/terminology#access-tokens">rate limit</Terminology>.          |
| `500`  | `internal_error`            | The <Terminology title="pfSense Actions itself, the go-between for your clients" to="/docs/reference/terminology#core-concepts">controller</Terminology> hit an unexpected error. |
| `502`  | `pfsense_unavailable`       | The SSH sign-in failed.                                                                                                                                                           |
| `502`  | `command_failed`            | `uname -mrs` failed, or the system information route got unexpected output.                                                                                                       |
| `503`  | `connection_not_configured` | No pfSense connection is saved yet, or its credential was removed.                                                                                                                |

The full list is in [Status Codes and Limits](/docs/api/status-codes/). A `502` or `500` also sends **Action failed** to the <Terminology title="Where an alert goes: ntfy, Telegram, email, webhook" to="/docs/reference/terminology#notifications">notification destinations</Terminology> that chose it, as described in [Notifications](/docs/console/notifications/#events).
